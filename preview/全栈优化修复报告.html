一、第一批 · 并发正确性

级别问题修复
P0 SQLite 未开 WAL，4 个任务线程 + 请求线程并发写同一 db 文件，默认 5s 锁等待 → 随机 database is locked，被 run_task 的 except 吞成「任务失败」 core/database.py 通过 @event.listens_for(engine,"connect") 挂 journal_mode=WAL / busy_timeout=30000 / synchronous=NORMAL / foreign_keys=ON；connect_args 加 timeout:30
P0 线程池待办队列无上限、无背压；海量提交 → 每个待办持有闭包与图片字节，内存无上限增长 task_runner.py 自维护 _inflight 计数（Lock 保护），超 _MAX_INFLIGHT（默认 workers×2，可配 TASK_MAX_INFLIGHT）抛 QueueFullError → API 层转 429（code 42901）
P0 _progress_sink 是模块级全局变量，4 个任务线程并行时互相覆盖，A 任务进度写到 B 任务通道 → 进度串台 改为 contextvars.ContextVar（线程池每任务线程独立 Context，天然隔离）；set_progress_sink 返回 token，新增 reset_progress_sink(token) 配对还原
P0 compliance_check 无 try/except，LLM 返回非 JSON → JSONDecodeError 直接打死整张图（与 qa_agent 有降级不一致） 包 try/except，异常时返回 passed=True + 「合规审查未执行，建议人工复核」feedback，流水线继续

二、第二批 · 安全

级别问题修复
P0 图片只限压缩后字节数，无像素上限：10MB PNG 可解压成数亿像素 → 内存炸弹 image/preprocess.py 设 Image.MAX_IMAGE_PIXELS = 40_000_000，open() 后 load() 前检查 pw×ph，并捕获 Image.DecompressionBombError → ImageProcessError
P1 SSRF：absolute_path(url) 对任意 URL 直接 httpx.get，无白名单，可探测内网 新增 assert_safe_remote_url(url, allowed_prefixes) 前缀白名单 + _is_private_host() 关键决策：_is_private_host 只对 IP 字面量判定，域名不做 DNS 解析——沙箱/生产的 DNS 会把公网域名解析到私网段（如 198.18.0.0/15）导致误判，前缀白名单才是主控制手段
P1 /files 中间件用原始 path 判 startswith("/files/")，漏掉 %2e%2e / /files/../files/x；防护依赖框架二次解析，一旦解析结果不一致即可绕过 新增 normalize_request_path()（unquote + PurePosixPath，返回 (规范化路径, 是否穿越)）；拒 .. 穿越、基于规范化路径判前缀、签名也基于规范化路径；统一 403 信封 {code:40300,…}
P0 任务状态机竞态：cancel / regenerate / 执行线程终态写入都是「读-改-写」，无原子性 → 取消被静默推翻、已完成任务被标取消 新增 _finish_task() 条件 UPDATE（只在 status NOT IN ('success','failed','cancelled') 时写终态）；cancel_task / schedule_regenerate 均改原子条件 UPDATE 消除 TOCTOU

三、第三批 · 性能与健壮性

级别问题修复
P1 SSE 生成器内直接跑同步阻塞 DB 查询 → 卡死整个 event loop，期间所有并发请求被拖住；且无断连检测，浏览器关闭后连接空转泄漏 查库改 await asyncio.to_thread(...)；每轮检查 request.is_disconnected()；加 SSE_MAX_DURATION=1800s 兜底回收半开连接 实测：流式进行中并发打 health 仍为 3ms
P1 rerank() 每次调用都 CrossEncoder(model) 重建模型（数百 MB 权重、数秒级加载），一条流水线重复多次，开销远超推理本身 rag/bm25.py 新增 _get_cross_encoder() 按模型名缓存；加载失败也缓存，避免反复重试注定失败的加载
P1 KB 检索缓存 key 含用户传入的 country/platform/category，属外部可控输入，无上界 → 构造大量过滤组合即可撑爆内存（value 还是整个语料 + BM25 索引） 两个缓存改 OrderedDict + _CACHE_MAX_ENTRIES=64 LRU 淘汰；命中走无锁快路径并 move_to_end 更新 LRU 顺序
P1 get_status 靠 lazy relationship 在属性访问时各发一条 SQL，/stream 每 0.5s 轮询一次 → N+1 放大成「轮询次数 × 3」条查询 改 selectinload(copy_versions, images) 显式一次性预加载，固定 3 条查询且同批完成
P1 extract_json 用 text[find("{"):rfind("}")] 截取：输出含多个 JSON 片段或说明文字里出现花括号时会截出非法片段 重写为「原文 → 代码块 → 平衡括号扫描」三段式：新增 _balanced_json_object() 按字符扫描并跟踪字符串状态（正确跳过字符串内花括号与转义），兼容顶层单对象数组；失败抛 ValueError 便于上层统一降级
P1 Retry-After 只用 isdigit() 判断，漏掉 RFC 7231 允许的 HTTP-date 格式 → 错误退回指数退避，等待时间与上游要求不符；anthropic.py 用 tenacity 完全不读 Retry-After 新增 _parse_retry_after() 同时支持秒数与 HTTP-date；anthropic.py 去掉 tenacity 改手写重试并复用该解析（含网络异常重试）
P1 recover_orphan_tasks 启动时把所有 running/pending 标记为 failed：多 worker 部署下 A 进程重启会误杀 B 进程正在执行的任务 改按心跳新鲜度判定：只回收 updated_at < now - 4×PROGRESS_HEARTBEAT_SEC（默认 12s）的；真在跑的任务每次进度落库都会刷新 updated_at，不会被误杀
P1 内存限流器 _hits 的 key 来自客户端 IP，外部可控且无上限 → 大量源 IP 打过来即内存泄漏 RateLimiter 加 max_keys=10000 上界：超限即扫（回收窗口内空桶 + 按插入序淘汰最老），保证是硬上界而非「平均意义上」有界
